# SQL 索引原理

> 分类：数据库 | 日期：2026-10-12 | 标签：sql, mysql, 优化

## B+ 树结构

MySQL（InnoDB）的索引底层是 **B+ 树**，几个关键特点：

- 多叉平衡树，树高通常只有 2~4 层，一次查询只需 2~4 次磁盘 IO。
- **非叶子节点只存键**（索引列的值），不存数据行，因此一个页（默认 16KB）能放更多键，扇出极大——千万级数据树高也才 3 层左右。
- **叶子节点**存放数据：主键索引（聚簇索引）直接挂完整行数据；二级索引挂主键值，查完还要"回表"再查一次主键索引。
- 叶子节点之间用双向链表串联，**范围查询和排序天然高效**（`WHERE id BETWEEN`、`ORDER BY` 顺着链表扫即可）。

## 为什么索引能加速查询

没有索引时只能全表扫描，复杂度 O(n)；有了 B+ 树索引，从根节点到叶子一路二分定位，等效 O(log n)。10 亿行的表按主键查，大约只需 4 次页读取。

```sql
-- 查看执行计划：type 至少要到 range，最好 ref / eq_ref / const
EXPLAIN SELECT * FROM orders WHERE user_id = 42;
```

EXPLAIN 重点看四列：`type`（访问类型）、`key`（实际使用的索引）、`rows`（预估扫描行数）、`Extra`（出现 Using filesort / Using temporary 就要警惕）。

## 索引失效的常见场景（易错点）

1. 对索引列做函数或运算：`WHERE YEAR(create_time) = 2026` 失效，应改写成范围条件 `create_time >= '2026-01-01' AND create_time < '2027-01-01'`。
2. 隐式类型转换：字符串列用数字查，如 `WHERE phone = 13800138000`，等价于对列做了 CAST。
3. 前导模糊匹配：`LIKE '%abc'` 失效；`LIKE 'abc%'` 可以走索引。
4. 联合索引不满足最左前缀：索引 (a, b, c)，只查 `WHERE b = 1` 用不上。
5. 范围查询之后的列失效：`WHERE a = 1 AND b > 5 AND c = 3` 中，c 无法使用索引。
6. `OR` 连接了没有索引的列，整个查询放弃索引。
7. 优化器评估回表成本过高或列区分度太低（如"性别"列），会主动放弃索引走全表——此时索引"看起来在却不走"。

## 实践建议

- 联合索引把**等值条件列放前面、范围列放最后**。
- 覆盖索引（查询的列全部包含在索引里）可避免回表，Extra 会显示 `Using index`；少写 `SELECT *`。
- 索引加速读但拖慢写：每次 INSERT/UPDATE/DELETE 都要维护 B+ 树，单表索引建议不超过 5~6 个。
- 字符串太长的列考虑前缀索引 `INDEX(email(20))`，但会失去覆盖索引能力。

## 我的理解

索引的本质是"用写放大换读加速"的有序结构。排查慢查询的固定动作：先 `EXPLAIN`，看走没走索引、扫描了多少行，再对着失效清单逐条核对写法，最后才考虑加索引。
